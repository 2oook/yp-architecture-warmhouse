### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут добавлять, изменять и удалять датчики.
- Пользователи могут вручную задавать значение и статус датчика (active/inactive).
- Система поддерживает один тип устройств - датчики температуры.

**Мониторинг температуры:**

- Пользователи могут получить список всех датчиков с текущей температурой.
- Пользователи могут получить температуру по конкретному датчику или по помещению.
- Система поддерживает получение показаний синхронно, в момент запроса, из внешнего temperature-api.
- Система не хранит историю показаний.

### 2. Анализ архитектуры монолитного приложения

- Язык: Go.
- База данных: PostgreSQL, одна таблица sensors, SQL-запросы без ORM.
- Архитектура: монолит - одно приложение, один процесс, одна БД.
- Взаимодействие компонентов: прямые вызовы внутри процесса; обработчики напрямую обращаются к БД и к сервису температуры, без отдельного слоя бизнес-логики.
- Внешние интеграции: синхронные HTTP-запросы к temperature-api за текущей температурой в момент запроса пользователя.
- API: REST, JSON.
- Развёртывание: Docker-образ, запуск через docker-compose.
- Масштабирование: только целиком, вертикально или запуском копий всего приложения.


### 3. Определение доменов и границы контекстов

В этом пункте задания LLM был использован для определения бизнес процессов в системе, разбиение на домены и поддомены без использования LLM.


1. Бизнес процессы системы:

Регистрация датчика - добавление нового датчика с указанием названия, типа, помещения и единицы измерения.

Управление датчиком - изменение данных датчика и его удаление.

Обновление данных датчика для управления отоплением - ручная запись значения и статуса.

Мониторинг температуры - получение текущей температуры по всем датчикам, по одному датчику или по помещению. Значение запрашивается у temperature-api в момент запроса.

2. Выделение доменов:

- Heating Management - домен управления отоплением
- Temperature Monitoring - домен контроля температуры

3. Выделение поддоменов:

Heating Management - можно разделить ещё на два поддомена:
- Sensor Management - управление инфраструктурой датчиков.
- Heating Control - управление непосредственно отоплением.

4. Определение контекстов:

- Sensor Management - Device Management Context
- Temperature Monitoring - Temperature Monitoring Context
- Heating Control - Heating Control Context

### **4. Проблемы монолитного решения**

- Нет возможности масштабировать горизонтально отдельный функционал при увеличении нагрузки.
- Существуют потенциальные сложности при расширении фнкционала системы т.к. из-за общей кодовой базы существует высокий риск ошибок (Изменения в одной части приложения могут непредсказуемо влиять на другие части).
- При целевом расширении функционала (включать и выключать свет, запирать и отпирать автоматические ворота, удалённо наблюдать за домом, возможно и т.д.) падает надёжность системы с целом - отказ одного компонента приведёт к отказу системы целиком.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия с API Gateway предлагаю использовать REST API т.к. такой тип API хорошо подходит для входной точки в приложение за счсёт человекочитаемости и относительно простоте тестирования.

Для взаимодействия микросервисов меджу собой пердлагаю использовать AsyncAPI Kafka т.к. сервисы не зависят друг от друга напрямую, отказ одного сервиса не останавливает остальные, события сохраняются и не теряются при перезапуске сервиса, на них легко подписать новые сервисы.

Для взаимодействия с устройствами предлагаю использовать MQTT: он подходит для устройств с ограниченными ресурсами.

Приложение temperature-api написано на C# (.NET 10), лежит в apps/temperature-api

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
